Q16. medium

Can you stack multiple decorators on one function? @a @b def f(): ...

@a
@b
def f(): ...
# equivalent to: f = a(b(f))
  1. A Yes - they apply bottom-up: f = a(b(f))
  2. B No, only one decorator per function
  3. C Yes, but they apply top-down: f = b(a(f))
  4. D Only if they take arguments

Answer: A — Yes - they apply bottom-up: f = a(b(f))

Decorators stack closest-first: b wraps f, then a wraps the result. Reading order matters - @a on top runs its 'before' code first at call time, but wraps last.

Q21. medium

Why might you prefer a CLOSURE over a full CLASS for simple state?

  1. A Less boilerplate when you only need one method plus some remembered state
  2. B Closures are always faster
  3. C Classes can't hold state
  4. D Closures support inheritance

Answer: A — Less boilerplate when you only need one method plus some remembered state

For a single behavior over some captured data (a counter, a multiplier, a validator), a closure is lighter than a class with __init__ and one method. For richer state/behavior, a class is clearer.

Q11. hard

After @deco wraps hello(), what does hello.__name__ show WITHOUT functools.wraps?

from functools import wraps
def deco(f):
    @wraps(f)          # preserves f's name/doc
    def wrapper(*a, **k):
        return f(*a, **k)
    return wrapper
  1. A 'wrapper' - the wrapper's name replaces the original, losing metadata
  2. B 'hello' - the name is preserved automatically
  3. C 'deco'
  4. D An empty string

Answer: A — 'wrapper' - the wrapper's name replaces the original, losing metadata

The decorated name now points to wrapper, so its __name__, __doc__ etc. are the wrapper's. This confuses debuggers and docs. functools.wraps copies the original's metadata onto the wrapper.

Q13. hard

How can a decorator itself take arguments? @repeat(3) def greet(): ...

def repeat(n):
    def decorator(func):
        def wrapper(*a, **k):
            for _ in range(n):
                func(*a, **k)
        return wrapper
    return decorator

@repeat(3)
def hi(): print("hi")   # prints hi 3 times
  1. A You need THREE nested functions - the outer takes the argument and returns the actual decorator
  2. B Decorators can't take arguments
  3. C Use @repeat, 3
  4. D Pass it to the wrapped function instead

Answer: A — You need THREE nested functions - the outer takes the argument and returns the actual decorator

@repeat(3) first CALLS repeat(3), which returns a decorator, which then wraps greet. That's three layers: repeat(n) -> decorator(func) -> wrapper(*args).

Q15. hard

What does @functools.lru_cache do?

from functools import lru_cache
@lru_cache
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
print(fib(50))   # instant, not slow
  1. A Caches a function's results so repeated calls with the same arguments return instantly
  2. B Limits how many times a function runs
  3. C Logs the function calls
  4. D Clears memory

Answer: A — Caches a function's results so repeated calls with the same arguments return instantly

lru_cache memoizes: it stores results by arguments. A slow recursive fib() becomes fast because repeated subproblems are looked up, not recomputed. LRU = Least Recently Used eviction when the cache is full.

MemoizationCaching

Q17. hard

What is the output? def make_multipliers(): return [lambda x: x * i for i in range(3)] print([m(10) for m in make_multipliers()])

# Fix with a default argument to capture the value:
[lambda x, i=i: x * i for i in range(3)]
# -> [0, 10, 20]
  1. A [20, 20, 20] - all lambdas share the SAME i, which ends at 2
  2. B [0, 10, 20]
  3. C [0, 20, 40]
  4. D [10, 10, 10]

Answer: A — [20, 20, 20] - all lambdas share the SAME i, which ends at 2

The lambdas close over the VARIABLE i, not its value at creation. By the time they run, the loop finished with i=2, so every lambda computes x*2 -> [20, 20, 20]. Classic closure trap.

Q18. hard

How do you FIX late-binding so each lambda captures its own i? [lambda x: x * i for i in range(3)]

mults = [lambda x, i=i: x * i for i in range(3)]
print([m(10) for m in mults])   # [0, 10, 20]
  1. A Add a default argument: [lambda x, i=i: x * i for i in range(3)]
  2. B Use global i
  3. C Remove the loop
  4. D It cannot be fixed

Answer: A — Add a default argument: [lambda x, i=i: x * i for i in range(3)]

Default arguments are evaluated at definition time, so i=i freezes the CURRENT value into each lambda. Now they give 0, 10, 20. (A factory function that takes i also works.)

Q24. hard

Why does a decorator usually RETURN the wrapper function instead of calling it?

  1. A The decorator replaces the original name; it must return a callable to be called later, not the result of one call
  2. B Returning is optional
  3. C To save memory
  4. D So the function runs immediately once

Answer: A — The decorator replaces the original name; it must return a callable to be called later, not the result of one call

@deco sets f = deco(f). If deco returned wrapper() (a result) instead of wrapper (the function), then f would be that result, and calling f() would fail. Return the function object.

Q26. hard

What is memoization (as done by a caching decorator)?

def memoize(f):
    cache = {}
    def wrapper(n):
        if n not in cache:
            cache[n] = f(n)
        return cache[n]
    return wrapper
  1. A Storing results of expensive calls and reusing them for repeated inputs
  2. B Writing memos in comments
  3. C Freeing memory automatically
  4. D Running a function in memory only

Answer: A — Storing results of expensive calls and reusing them for repeated inputs

Memoization trades memory for speed: a dict maps arguments to results, so a repeated call is a lookup, not a recomputation. A decorator is the clean way to add it. lru_cache does exactly this.
