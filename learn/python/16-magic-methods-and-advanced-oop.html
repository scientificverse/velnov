Q1. easy

What are 'magic methods' (dunder methods)?

  1. A Methods with double underscores (__str__, __len__...) that hook your class into Python's built-in behavior
  2. B Methods that run magically fast
  3. C Hidden methods you can't call
  4. D Deprecated Python 2 methods

Answer: A — Methods with double underscores (__str__, __len__...) that hook your class into Python's built-in behavior

'Dunder' = Double UNDERscore. Python calls them automatically: print(obj) calls __str__, len(obj) calls __len__, a + b calls __add__. Define them to make your objects behave like built-ins.

Dunder methodsProtocols

Q2. easy

Which method controls what print(obj) displays?

class Book:
    def __init__(self, title):
        self.title = title
    def __str__(self):
        return f"Book: {self.title}"

print(Book("Dune"))   # Book: Dune
  1. A __str__
  2. B __print__
  3. C __show__
  4. D __display__

Answer: A — __str__

__str__ returns the human-readable text for your object - used by print(), str() and f-strings. Without it you get the ugly <__main__.X object at 0x...>.

Q5. medium

Which method makes == compare your objects by CONTENT?

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

print(Point(1, 2) == Point(1, 2))   # True
  1. A __eq__
  2. B __equals__
  3. C __compare__
  4. D __is__

Answer: A — __eq__

a == b calls a.__eq__(b). Without it, == falls back to identity (same object?). Define it to compare data instead.

__eq__Equality

Q6. medium

Which method lets you write v1 + v2 for your own Vector class?

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)

v = Vector(1, 2) + Vector(3, 4)
print(v.x, v.y)   # 4 6
  1. A __add__
  2. B __plus__
  3. C __sum__
  4. D add()

Answer: A — __add__

v1 + v2 calls v1.__add__(v2) - operator overloading. Return a NEW object with the combined values. Siblings: __sub__ (-), __mul__ (*), __truediv__ (/).

Operator overloading__add__

class MathUtils:

Answer: A — A method that gets NO automatic self/cls - a plain function stored in the class for organization

Q19. medium

Which method decides your object's truthiness in 'if obj:'?

class Cart:
    def __init__(self):
        self.items = []
    def __len__(self):
        return len(self.items)

if not Cart():
    print("empty cart")   # prints!
  1. A __bool__ (falling back to __len__ != 0 if absent)
  2. B __true__
  3. C __if__
  4. D Objects are always False

Answer: A — __bool__ (falling back to __len__ != 0 if absent)

if cart: calls cart.__bool__() - or, if undefined, treats the object as truthy unless __len__ returns 0. That's why empty custom containers naturally read as falsy once __len__ exists.

Q20. medium

Why is c.area (a @property) better Python style than c.get_area()?

  1. A Attribute syntax is cleaner, and you can start as a plain attribute and add logic later WITHOUT breaking callers
  2. B get_ methods are illegal
  3. C Properties are faster
  4. D No reason - Java style is preferred

Answer: A — Attribute syntax is cleaner, and you can start as a plain attribute and add logic later WITHOUT breaking callers

In Java you write getters defensively from day one. Python lets you expose a plain attribute now and transparently swap in a @property later - same c.area syntax for callers. So write simple attributes first; add properties only when logic is needed.

@propertyAPI design

Q23. medium

Does Python have truly PRIVATE attributes like Java's private keyword?

  1. A No - only conventions (_x) and name mangling (__x); everything remains reachable
  2. B Yes - the private keyword
  3. C Yes - via @private
  4. D Only in classes marked sealed

Answer: A — No - only conventions (_x) and name mangling (__x); everything remains reachable

Python chose openness: nothing is enforced-private. _x says 'don't', __x adds mangling, but a determined caller can reach anything. Discipline over locks.

Q26. medium

Which dunder pair powers the WITH statement (context managers)?

class Timer:
    def __enter__(self):
        self.start = time.time()
        return self
    def __exit__(self, *args):
        print(f"took {time.time() - self.start:.2f}s")

with Timer():
    do_work()
  1. A __enter__ and __exit__
  2. B __open__ and __close__
  3. C __start__ and __stop__
  4. D __with__ and __without__

Answer: A — __enter__ and __exit__

with obj: calls obj.__enter__() at the start and obj.__exit__() at the end - ALWAYS, even on exceptions. Define both and your class works in with statements, like open() does.

Q3. hard

What is the difference between __str__ and __repr__?

class Book:
    def __repr__(self):
        return f"Book({self.title!r})"

books = [Book("Dune")]
print(books)   # [Book('Dune')] - repr used inside lists!
  1. A __str__ is the friendly display for users; __repr__ is the unambiguous version for developers/debugging (shown in the REPL and inside lists)
  2. B They are interchangeable aliases
  3. C __repr__ repeats the string twice
  4. D __str__ is Python 2 only

Answer: A — __str__ is the friendly display for users; __repr__ is the unambiguous version for developers/debugging (shown in the REPL and inside lists)

print(obj) uses __str__; typing obj in the shell, or printing a LIST of objects, uses __repr__. Convention: __repr__ looks like the code to recreate the object: Book('Dune'). If you define only one, define __repr__ - str falls back to it.

__repr__Debugging

class Student:

sorted() compares elements with < - so one __lt__ makes lists of your objects sortable. (functools.total_ordering can derive the other comparisons from __lt__ + __eq__.)

What does a DOUBLE leading underscore do: self.__secret?

class Account:
    def __init__(self):
        self.__pin = 1234

a = Account()

  1. A Name mangling - Python renames it to _ClassName__secret, making accidental outside access harder
  2. B Makes it 100% inaccessible

__secret becomes _Account__secret internally - obj.__secret fails with AttributeError, though obj._Account__secret still works (so it's tamper-resistant, not secure). Main real use: avoiding name clashes in subclasses.

Class methods get the class as their first argument (named cls). Their killer use: ALTERNATIVE CONSTRUCTORS - building instances from different input formats.

Q18. hard

What is the true division of labor between __new__ and __init__?

  1. A __new__ CREATES the object; __init__ then INITIALIZES the already-created object
  2. B __init__ creates, __new__ initializes
  3. C They are aliases
  4. D __new__ is Python 2 only

Answer: A — __new__ CREATES the object; __init__ then INITIALIZES the already-created object

Calling Dog() first runs __new__ (allocates the instance) then __init__ (fills in attributes). You almost never touch __new__ - exceptions: immutable subclasses and singletons. Strictly, __init__ is an initializer, not a constructor.

Q25. hard

v * 3 works on your Vector but 3 * v fails. Which method fixes the reversed order?

class Vector:
    def __mul__(self, n):

  1. A __rmul__
  2. B __mul2__
  3. C __xmul__
  4. D It cannot be fixed

Answer: A — __rmul__

3 * v first tries (3).__mul__(v) - int doesn't know Vector, so Python then tries v.__rmul__(3). The r-prefixed 'reflected' methods handle your object on the RIGHT side of an operator.

Q28. hard

What is a SINGLETON, and which method is typically overridden to make one?

class Config:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

print(Config() is Config())   # True
  1. A A class allowing only ONE instance ever - override __new__ to return the same stored instance
  2. B A class with one method - override __init__
  3. C A single-file module
  4. D An unmarried class

Answer: A — A class allowing only ONE instance ever - override __new__ to return the same stored instance

__new__ controls creation, so it can hand back a cached instance instead of a fresh one - every Config() call returns the same object. (In practice, a module-level instance is often the simpler Python singleton.)
