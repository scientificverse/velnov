What is the first step to optimise a slow query?

  1. A Run EXPLAIN to see the execution plan and identify scans, missing indexes or bad join orders
  2. B Add more RAM
  3. C Rewrite it randomly
  4. D Drop the table

Q20. medium

Why avoid SELECT * in production queries?

  1. A It transfers unneeded columns, prevents covering indexes, and breaks if the schema changes
  2. B It is a syntax error
  3. C It is always faster
  4. D No reason

Answer: A — It transfers unneeded columns, prevents covering indexes, and breaks if the schema changes

Selecting only needed columns reduces I/O and network transfer and can let an index satisfy the query entirely (covering index). It also makes code resilient to column changes.

Q1. hard

What is a window function?

SELECT name, dept, salary,
  AVG(salary) OVER (PARTITION BY dept) AS dept_avg
FROM employees;
  1. A A function that computes across a set of rows RELATED to the current row, without collapsing them into one
  2. B A GUI feature
  3. C The same as GROUP BY
  4. D A type of index

Answer: A — A function that computes across a set of rows RELATED to the current row, without collapsing them into one

Unlike aggregates with GROUP BY (which return one row per group), window functions add a computed column while KEEPING every row - perfect for running totals, ranks and comparisons to a group.

Window functionsOVER

Q2. hard

What does the OVER() clause define?

  1. A The 'window' of rows the function operates on - via PARTITION BY and ORDER BY
  2. B Which table to use
  3. C The output format
  4. D An index

Answer: A — The 'window' of rows the function operates on - via PARTITION BY and ORDER BY

OVER() is what makes a function a window function. Empty OVER() means the whole result set; PARTITION BY splits it into groups; ORDER BY orders rows within each partition.

OVERPARTITION BY

  2. B They are identical
  3. C Window functions delete rows
  4. D GROUP BY keeps all rows

Answer: A — GROUP BY collapses rows into one per group; a window function keeps all rows and adds the computed value to each

To show each employee's salary alongside their department average WITHOUT losing individual rows, you need a window function. GROUP BY would leave you with one row per department.

Q5. hard

What does ROW_NUMBER() OVER (ORDER BY marks DESC) produce?

  1. A A sequential number 1, 2, 3... assigned by descending marks - unique even for ties
  2. B The same number for ties
  3. C The marks value
  4. D A random number

Answer: A — A sequential number 1, 2, 3... assigned by descending marks - unique even for ties

ROW_NUMBER always gives distinct consecutive numbers, breaking ties arbitrarily. It is the tool for 'give me the top N per group' and for de-duplication.

Q6. hard

What is the difference between RANK() and DENSE_RANK()?

SELECT name, RANK() OVER (ORDER BY marks DESC) AS r,
            DENSE_RANK() OVER (ORDER BY marks DESC) AS dr
FROM students;
  1. A RANK leaves gaps after ties (1,1,3); DENSE_RANK does not (1,1,2)
  2. B They are identical
  3. C DENSE_RANK leaves gaps
  4. D RANK never allows ties

Answer: A — RANK leaves gaps after ties (1,1,3); DENSE_RANK does not (1,1,2)

With two rows tied at rank 1, RANK gives the next row rank 3 (skipping 2), while DENSE_RANK gives it rank 2. ROW_NUMBER would give 1 and 2 to the tied rows.

RANKDENSE_RANK

Q7. hard

How do you find the top 3 earners PER DEPARTMENT?

WITH r AS (
  SELECT *, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) rk FROM emp
)
SELECT * FROM r WHERE rk <= 3;
  1. A Use ROW_NUMBER/RANK OVER (PARTITION BY dept ORDER BY salary DESC) and filter <= 3 in an outer query
  2. B ORDER BY salary LIMIT 3
  3. C GROUP BY dept HAVING salary
  4. D MAX(salary)

Answer: A — Use ROW_NUMBER/RANK OVER (PARTITION BY dept ORDER BY salary DESC) and filter <= 3 in an outer query

You cannot filter a window function in WHERE (it is computed after WHERE), so wrap it in a subquery/CTE and filter the rank there. This 'top N per group' is a classic window-function use.

Q8. hard

Why can't you filter a window function's result in WHERE?

  1. A Window functions are computed AFTER WHERE (during SELECT), so the value does not exist yet - use a subquery/CTE
  2. B It is a syntax preference
  3. C You can filter them in WHERE
  4. D They run first

Answer: A — Window functions are computed AFTER WHERE (during SELECT), so the value does not exist yet - use a subquery/CTE

Execution order places window functions after WHERE and GROUP BY. To filter on rank or a running total, compute it in a CTE and apply WHERE in the outer query.

Q9. hard

What does a running total look like with window functions?

SELECT date, amount,
  SUM(amount) OVER (ORDER BY date) AS running_total
FROM transactions;
  1. A SUM(amount) OVER (ORDER BY date) - accumulates as rows progress
  2. B SUM(amount) GROUP BY date
  3. C SUM(amount) OVER () only
  4. D It is impossible

Answer: A — SUM(amount) OVER (ORDER BY date) - accumulates as rows progress

Adding ORDER BY to a windowed SUM makes it a running total (cumulative sum) up to the current row. PARTITION BY resets it per group (e.g. running total per account).

Running totalSUM OVER

Q10. hard

What do LAG() and LEAD() do?

SELECT month, sales,
  sales - LAG(sales) OVER (ORDER BY month) AS change
FROM monthly;
  1. A Access a value from a PREVIOUS (LAG) or NEXT (LEAD) row - useful for period-over-period comparisons
  2. B Sort rows
  3. C Lag the query
  4. D Delete rows

Answer: A — Access a value from a PREVIOUS (LAG) or NEXT (LEAD) row - useful for period-over-period comparisons

LAG(sales) OVER (ORDER BY month) gives last month's sales on the current row, so you can compute growth. LEAD looks forward. Both replace awkward self joins.

LAGLEAD

Q11. hard

How do you compute month-over-month growth?

  1. A sales - LAG(sales) OVER (ORDER BY month) - compare each row to the previous
  2. B SUM(sales) GROUP BY month
  3. C MAX(sales) - MIN(sales)
  4. D It cannot be done

Answer: A — sales - LAG(sales) OVER (ORDER BY month) - compare each row to the previous

LAG pulls the prior month's value into the current row, so a simple subtraction gives the change. Divide by the lagged value for a percentage.

LAGGrowth

Q13. hard

  1. A The first or last value in the window's ordered frame - e.g. the earliest order per customer

  3. C The row count
  4. D The current row

Answer: A — The first or last value in the window's ordered frame - e.g. the earliest order per customer

FIRST_VALUE(price) OVER (PARTITION BY product ORDER BY date) gives the earliest price on every row. LAST_VALUE needs a full frame clause to work as expected, a common gotcha.

Q15. hard

What is the default frame when you use ORDER BY in OVER() without ROWS?

  1. A RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW - a running total up to the current row (including ties)
  2. B The whole partition
  3. C Only the current row
  4. D No frame

This default is why SUM(...) OVER (ORDER BY x) is a running total. It also explains the LAST_VALUE surprise: the default frame ends at the current row, not the partition end.

Numbering rows per key by recency and keeping rn = 1 selects the latest per group while retaining its other columns - which DISTINCT and GROUP BY cannot do cleanly.

  3. C It scans twice

Q22. hard

What is the N+1 query problem?

  1. A Running one query per row of a previous result (in application code) instead of a single join - very slow
  2. B A window function
  3. C An index type
  4. D A transaction level

Answer: A — Running one query per row of a previous result (in application code) instead of a single join - very slow

Q27. hard

How do you compute a 7-day moving average?

  2. B AVG(value) GROUP BY date
  3. C AVG(value) OVER ()

The frame ROWS BETWEEN 6 PRECEDING AND CURRENT ROW includes the current day plus the six before it - a 7-row moving average. Frames make time-series smoothing straightforward.

What is the single best mindset for query optimization?

  2. B Guess and add random hints
