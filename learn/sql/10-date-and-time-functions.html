Easy questions (2)

Q1. easy

Which function returns the current date and time?

SELECT NOW();   -- 2026-07-04 14:30:05
  1. A NOW() (or CURRENT_TIMESTAMP)
  2. B TODAY()
  3. C DATE()
  4. D TIME.NOW

Answer: A — NOW() (or CURRENT_TIMESTAMP)

NOW() and CURRENT_TIMESTAMP return the current moment. CURRENT_DATE gives just the date, and CURRENT_TIME just the clock. (SQL Server uses GETDATE().)

Q2. easy

What is the standard SQL date format?

WHERE order_date = '2026-07-04';
  1. A 'YYYY-MM-DD' - year, month, day
  2. B 'DD-MM-YYYY'
  3. C 'MM/DD/YYYY'
  4. D 'DD/MM/YY'

Answer: A — 'YYYY-MM-DD' - year, month, day

ISO 8601 format 'YYYY-MM-DD' is unambiguous and sorts correctly as text. Always use it in queries to avoid locale confusion between month and day.

Q3. medium

How do you extract just the YEAR from a date?

SELECT EXTRACT(YEAR FROM order_date), EXTRACT(MONTH FROM order_date);
  1. A EXTRACT(YEAR FROM order_date) or YEAR(order_date)
  2. B GET_YEAR(order_date)
  3. C order_date.year
  4. D DATEYEAR(order_date)

Answer: A — EXTRACT(YEAR FROM order_date) or YEAR(order_date)

EXTRACT is standard SQL; MySQL and SQL Server also have YEAR(), MONTH(), DAY() shortcuts. EXTRACT(DOW FROM d) even gives the day of week.

EXTRACTYEAR

Q4. medium

How do you add 7 days to a date?

SELECT order_date + INTERVAL '7 days' AS due_date FROM orders;
  1. A order_date + INTERVAL '7 days' or DATE_ADD(order_date, INTERVAL 7 DAY)
  2. B order_date + 7 (always works)
  3. C ADD_DAYS(order_date, 7)
  4. D order_date.plus(7)

Answer: A — order_date + INTERVAL '7 days' or DATE_ADD(order_date, INTERVAL 7 DAY)

PostgreSQL/Oracle use INTERVAL; MySQL uses DATE_ADD; SQL Server uses DATEADD(DAY, 7, order_date). Plain + 7 works on DATE in some databases but is not portable.

DATE_ADDINTERVAL

Q5. medium

How do you find the number of days between two dates?

SELECT DATEDIFF(delivered_at, ordered_at) AS days_to_deliver FROM orders;
  1. A DATEDIFF(end_date, start_date) or end_date - start_date
  2. B DAYS_BETWEEN only
  3. C SUBTRACT(end, start)
  4. D end.minus(start)

Answer: A — DATEDIFF(end_date, start_date) or end_date - start_date

In PostgreSQL, subtracting two DATEs gives an integer number of days. MySQL uses DATEDIFF(end, start); SQL Server uses DATEDIFF(DAY, start, end) - note the argument order differs.

Q7. medium

How do you get the first day of the current month?

SELECT DATE_TRUNC('month', order_date) AS month, COUNT(*)
FROM orders GROUP BY 1;
  1. A DATE_TRUNC('month', CURRENT_DATE) in PostgreSQL
  2. B MONTH_START()
  3. C FIRST_DAY()
  4. D CURRENT_DATE - 30

Answer: A — DATE_TRUNC('month', CURRENT_DATE) in PostgreSQL

DATE_TRUNC rounds a date down to a unit (month, year, hour). It is the cleanest way to bucket timestamps for reporting. MySQL uses DATE_FORMAT or arithmetic.

Q9. medium

How do you extract the day of the week?

  1. A EXTRACT(DOW FROM date) or DAYOFWEEK(date) - returns a number for the weekday
  2. B WEEKDAY_NAME(date)
  3. C DAY(date)
  4. D There is no way

Answer: A — EXTRACT(DOW FROM date) or DAYOFWEEK(date) - returns a number for the weekday

Beware the numbering differs: PostgreSQL DOW is 0=Sunday, MySQL DAYOFWEEK is 1=Sunday, and ISODOW is 1=Monday. Check your database before filtering on weekdays.

Answer: A — The date portion only, dropping the time

Q12. medium

How do you calculate age in years from a birthdate?

  1. A AGE(birthdate) in PostgreSQL, or DATEDIFF-based arithmetic elsewhere
  2. B birthdate - NOW()
  3. C YEARS(birthdate)
  4. D birthdate.age()

Answer: A — AGE(birthdate) in PostgreSQL, or DATEDIFF-based arithmetic elsewhere

PostgreSQL's AGE() returns an interval; extract the years. Elsewhere: FLOOR(DATEDIFF(NOW(), birthdate) / 365.25), being careful about leap years and exact birthdays.

Q13. medium

How do you filter for records from the last 30 days?

WHERE created_at >= NOW() - INTERVAL '30 days';
  1. A WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
  2. B WHERE created_at = LAST_30_DAYS
  3. C WHERE created_at IN (30 days)
  4. D WHERE RECENT(created_at, 30)

Answer: A — WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'

Compute the cutoff by subtracting an interval from today, then compare. Keeping the function on the constant side (not the column) lets the index on created_at work.

Q15. medium

How do you format a date as 'July 04, 2026'?

  1. A TO_CHAR(order_date, 'Month DD, YYYY') in PostgreSQL/Oracle
  2. B FORMAT(order_date)
  3. C STRING(order_date)
  4. D Dates cannot be formatted

Answer: A — TO_CHAR(order_date, 'Month DD, YYYY') in PostgreSQL/Oracle

TO_CHAR with a format model handles custom display. MySQL uses DATE_FORMAT(date, '%M %d, %Y'); SQL Server uses FORMAT(). Prefer formatting in the app layer where possible.

Q17. medium

How do you get yesterday's date?

  1. A CURRENT_DATE - INTERVAL '1 day' (or CURRENT_DATE - 1 in some databases)
  2. B YESTERDAY()
  3. C NOW() - 1
  4. D PREVIOUS(CURRENT_DATE)

Answer: A — CURRENT_DATE - INTERVAL '1 day' (or CURRENT_DATE - 1 in some databases)

Subtracting an interval is the portable form. In PostgreSQL and MySQL, CURRENT_DATE - 1 also works because a DATE minus an integer subtracts days.

INTERVALDate arithmetic

Q19. medium

What does EXTRACT(EPOCH FROM interval) give in PostgreSQL?

  1. A The interval expressed in total SECONDS
  2. B The year
  3. C The month name
  4. D An error

Answer: A — The interval expressed in total SECONDS

EPOCH converts an interval or timestamp to seconds - useful for computing precise durations like average response time: EXTRACT(EPOCH FROM (ended - started)).

Q20. medium

How do you get the last day of a month?

  1. A LAST_DAY(date) in MySQL/Oracle, or date-arithmetic with DATE_TRUNC in PostgreSQL
  2. B MONTH_END(date)
  3. C date + 30
  4. D FINAL_DAY(date)

Answer: A — LAST_DAY(date) in MySQL/Oracle, or date-arithmetic with DATE_TRUNC in PostgreSQL

LAST_DAY handles varying month lengths and leap years automatically. In PostgreSQL: (DATE_TRUNC('month', d) + INTERVAL '1 month - 1 day').

Q28. medium

How do you find records from the current year?

  1. A WHERE order_date >= DATE_TRUNC('year', CURRENT_DATE)
  2. B WHERE YEAR(order_date) = THIS_YEAR
  3. C WHERE order_date = 2026
  4. D WHERE order_date CONTAINS 2026

Answer: A — WHERE order_date >= DATE_TRUNC('year', CURRENT_DATE)

Truncating today's date to the year gives January 1st, and comparing with >= keeps the index usable - better than wrapping the column in YEAR().

Q30. medium

Which is the safest, most portable literal for a specific date-time?

  1. A '2026-07-04 14:30:00' - ISO format, understood everywhere
  2. B 'July 4 2026 2:30pm'
  3. C '04-07-26'
  4. D '7/4/26 14:30'

Answer: A — '2026-07-04 14:30:00' - ISO format, understood everywhere

ISO 8601 (YYYY-MM-DD HH:MM:SS) is unambiguous and sorts correctly. The other formats depend on locale settings and are a frequent source of silent misreads.

Q6. hard

Why does 'WHERE order_date = '2026-07-04'' sometimes miss rows?

  1. A If the column stores a time too, only rows at exactly midnight match; use a date range instead
  2. B The date format is wrong
  3. C Dates cannot be compared with =
  4. D It never misses rows

Answer: A — If the column stores a time too, only rows at exactly midnight match; use a date range instead

A DATETIME of 2026-07-04 14:30 is not equal to 2026-07-04 00:00. Use a half-open range: order_date >= '2026-07-04' AND order_date < '2026-07-05'.

Q8. hard

How do you group sales by month correctly across multiple years?

  1. A GROUP BY DATE_TRUNC('month', sale_date) - keeps year and month together
  2. B GROUP BY MONTH(sale_date) - merges same months across years
  3. C GROUP BY sale_date
  4. D GROUP BY YEAR(sale_date) only

Answer: A — GROUP BY DATE_TRUNC('month', sale_date) - keeps year and month together

GROUP BY MONTH() alone would merge January 2025 and January 2026 into one bucket. DATE_TRUNC (or grouping by both YEAR and MONTH) keeps them separate.

Q11. hard

Why is storing timestamps in UTC recommended?

  1. A It avoids ambiguity across timezones and daylight-saving changes; convert to local time only for display
  2. B UTC is faster to store
  3. C Local time never changes
  4. D It uses less space

Answer: A — It avoids ambiguity across timezones and daylight-saving changes; convert to local time only for display

Storing local times means a value can be ambiguous (a clock hour can occur twice) or missing (during a spring-forward). UTC is a single monotonic reference; format it per-user at display time.

Q16. hard

What is the difference between TIMESTAMP and TIMESTAMPTZ (PostgreSQL)?

  1. A TIMESTAMPTZ is timezone-aware and stores an absolute instant; TIMESTAMP stores a 'wall clock' with no zone
  2. B They are identical
  3. C TIMESTAMPTZ cannot store time
  4. D TIMESTAMP is newer

Answer: A — TIMESTAMPTZ is timezone-aware and stores an absolute instant; TIMESTAMP stores a 'wall clock' with no zone

TIMESTAMPTZ converts input to UTC on storage and back to the session zone on display. For anything user-facing across regions, TIMESTAMPTZ is usually the right choice.

  1. A WHERE created_at >= CURRENT_DATE AND created_at < CURRENT_DATE + INTERVAL '1 day'

Q27. hard

  1. A Use a plain DATE type when time-of-day is irrelevant (e.g. a birthday or invoice date)
  2. B Always store as text
  3. C Store as an integer offset

Answer: A — Use a plain DATE type when time-of-day is irrelevant (e.g. a birthday or invoice date)
