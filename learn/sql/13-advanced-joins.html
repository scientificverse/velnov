Easy questions (1)

Q4. easy

What does CROSS JOIN produce?

SELECT s.size, c.color FROM sizes s CROSS JOIN colors c;
  1. A The Cartesian product - every row of A combined with every row of B
  2. B Only matching rows
  3. C All left rows
  4. D Nothing

Answer: A — The Cartesian product - every row of A combined with every row of B

CROSS JOIN has no ON condition. 5 rows crossed with 4 rows gives 20. Useful for generating combinations like every size/colour pairing.

Medium questions (14)

Q1. medium

What is a SELF JOIN?

SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id;
  1. A Joining a table to ITSELF using two aliases
  2. B A join that repeats automatically
  3. C A join with no condition
  4. D A join between two databases

Answer: A — Joining a table to ITSELF using two aliases

The same table appears twice under different aliases, letting you relate rows within one table - such as employees to their managers.

Q2. medium

Why are aliases mandatory in a self join?

  1. A Both sides are the same table, so aliases distinguish the two roles and remove ambiguity
  2. B For speed
  3. C To sort the rows
  4. D They are optional

Answer: A — Both sides are the same table, so aliases distinguish the two roles and remove ambiguity

Without aliases like e and m, the database cannot tell which 'name' or 'id' you mean. Aliases give each copy of the table a distinct identity.

Q17. medium

Can CROSS JOIN be combined with a WHERE clause?

  1. A Yes - and a CROSS JOIN plus a WHERE equality condition is effectively an INNER JOIN
  2. B No, CROSS JOIN forbids WHERE
  3. C Only with ON
  4. D It errors

Answer: A — Yes - and a CROSS JOIN plus a WHERE equality condition is effectively an INNER JOIN

FROM a CROSS JOIN b WHERE a.id = b.a_id filters the product down to matches - the old implicit-join style. Explicit INNER JOIN ON expresses the same intent more safely.

Q3. hard

How do you find pairs of employees in the SAME department (without duplicates)?

  1. A Self join ON a.dept = b.dept AND a.id < b.id
  2. B Self join ON a.dept = b.dept
  3. C INNER JOIN with GROUP BY
  4. D CROSS JOIN

Answer: A — Self join ON a.dept = b.dept AND a.id < b.id

The a.id < b.id condition prevents matching a row with itself and avoids listing each pair twice (A-B and B-A). A classic self-join interview question.

Q6. hard

What is an accidental Cartesian product, and how does it happen?

  1. A A huge result from a missing or wrong join condition - rows multiply instead of matching
  2. B A deliberate CROSS JOIN
  3. C A type of index
  4. D An empty result

Answer: A — A huge result from a missing or wrong join condition - rows multiply instead of matching

Forgetting ON (or a comma-join without WHERE) pairs every row with every row. Two 10,000-row tables produce 100 million rows - a common cause of runaway queries.

Q7. hard

How do you build a hierarchy of unlimited depth (e.g. org chart)?

  1. A A recursive CTE (WITH RECURSIVE) - a self join only reaches a fixed number of levels
  2. B Nested self joins forever
  3. C CROSS JOIN
  4. D It is impossible

Answer: A — A recursive CTE (WITH RECURSIVE) - a self join only reaches a fixed number of levels

Each self join adds exactly one level. For arbitrary depth (manager of manager of ...), a recursive CTE walks the tree. (CTEs are covered in topic 15.)

Q9. hard

In a multi-table join, why can row counts balloon unexpectedly?

  1. A Each one-to-many join multiplies rows - joining orders to items AND to payments can multiply items by payments
  2. B Joins always reduce rows
  3. C It is a syntax error
  4. D Only with CROSS JOIN

Answer: A — Each one-to-many join multiplies rows - joining orders to items AND to payments can multiply items by payments

If an order has 3 items and 2 payments, joining both to the order yields 3 x 2 = 6 rows. Aggregate each branch separately (in subqueries) before combining to avoid inflated totals.

  • A hard-to-spot cause of wrong sums in reports.

Q12. hard

What is a non-equi join?

SELECT s.id, t.discount
FROM sales s JOIN tiers t ON s.amount BETWEEN t.min_amt AND t.max_amt;
  1. A A join whose condition uses something other than equality (<, >, BETWEEN)
  2. B A join with no condition
  3. C An invalid join
  4. D A join on two equal columns

Answer: A — A join whose condition uses something other than equality (<, >, BETWEEN)

For example joining sales to a tier table ON amount BETWEEN tier.low AND tier.high to assign a discount band. Equality is common but not required.

  4. D It is impossible

Answer: A — CROSS JOIN or a recursive CTE / generate_series to produce all dates, then LEFT JOIN the data

What does LATERAL / CROSS APPLY allow?

SELECT c.name, o.total
FROM customers c

LATERAL (PostgreSQL) and CROSS APPLY (SQL Server) let a join's right side depend on the left row - perfect for 'top 3 orders per customer'.

Q21. hard

In a query joining orders, items and payments, how do you avoid inflated sums?

  1. A Aggregate items and payments in SEPARATE subqueries first, then join the summaries to orders
  2. B Use DISTINCT on everything
  3. C Join all three directly and SUM
  4. D Use CROSS JOIN

Answer: A — Aggregate items and payments in SEPARATE subqueries first, then join the summaries to orders

Joining two one-to-many branches multiplies rows. Pre-aggregating each branch to one row per order removes the fan-out before you combine them.

Q25. hard

How does an anti-join differ from a semi-join?

  1. A Semi-join keeps left rows that HAVE a match (EXISTS); anti-join keeps those that have NO match (NOT EXISTS)
  2. B They are the same
  3. C Semi-join duplicates rows
  4. D Anti-join is invalid

Answer: A — Semi-join keeps left rows that HAVE a match (EXISTS); anti-join keeps those that have NO match (NOT EXISTS)

EXISTS is a semi-join (existence test, no fan-out). NOT EXISTS or LEFT JOIN ... IS NULL is an anti-join. Both return left columns only, unlike a normal join.

Q27. hard

Why can a range self join (t.value BETWEEN a AND b) be slow?

  1. A Range conditions are harder to index than equality, often forcing more comparisons
  2. B It is always fast
  3. C Ranges are not allowed in joins
  4. D It errors

Answer: A — Range conditions are harder to index than equality, often forcing more comparisons

Equality joins can use hash/merge strategies efficiently; range joins often fall back to nested loops. Appropriate indexes and small tier tables keep them manageable.
